# Telegram-бот дайджестов по стройкам из Битрикс24 — Спецификация

> Этот документ самодостаточен. Его можно передать Claude Code (или разработчику) как техническое задание для сборки MVP. Все решения ниже уже согласованы.
>
> **Ревизия 2 (2026-07-21).** Спека вычитана с факт-чеком по официальным докам Bitrix24 и Telegram Bot API + приняты решения владельца. Ключевые изменения против ревизии 1: комментарии читаются из **чата задачи** (`task.commentitem.*` deprecated и не работает в новой карточке), курсор дельты — **per (карточка, чат)** и двигается только после успешной отправки, время дайджеста — **per-country**, хостинг MVP — **сервер MUSPELHEIM** вместо ноутбука, privacy mode бота **остаётся включённым** (Фаза 3 работает на командах и reply, без @упоминаний).

---

## 1. Цель

Бот несколько раз в день — в фиксированные локальные часы `DIGEST_HOURS` (9/11/13/15/17/19 по таймзоне чата) — собирает апдейты по строящимся пиццериям из карточек-задач Битрикс24 и, если есть изменения, публикует дайджест в конкретный топик стройки в чате страны (Telegram-супергруппа). Тексты формируются через LLM (OpenAI). Партнёры настраивают бота сами через команды в чате. Поддержка нескольких языков.

## 2. Контекст

- Международная сеть пиццерий, экспансия по странам (сейчас ~24 страны).
- В каждой стране 1–4 строящиеся пиццерии.
- Весь процесс стройки (согласование материалов, обсуждение, файлы) ведётся в **задаче Битрикса**, которую внутри называют «карточкой». Обсуждение идёт в комментариях, к комментариям прикладываются файлы (планировки, интерьерные рендеры и т.п.).
- Также в задаче есть чек-лист — его состояние тоже важно отслеживать.
- Портал — **коробочный** Битрикс (`b24.dodoteam.ru`), НЕ облако. Живой смоук (2026-07-23, карточка 42103): карточки **старого типа** — у задач нет чата (`chatId` отсутствует), комментарии живут в старом comment-API (`task.commentitem.getlist` работает). Поэтому основной путь чтения на этом портале — fallback по комментариям (§7 п.2, курсор `last_comment_id`); путь через чат задачи (`im.dialog.messages.get`) сохранён в коде на случай обновления портала. Портал прикрыт антиботом Servicepipe: POST к REST режется JS-challenge'ем, GET с браузерным User-Agent проходит — клиент ходит GET-ом (§13); запрошено WAF-исключение по маркеру `construction-bot` в UA.

## 3. Модель данных (три уровня)

- **Страна** = супергруппа Telegram + один конкретный топик стройки (`chat_id` + `message_thread_id`).
- **Пиццерия** (например «Бишкек 8», «Бишкек 10») = одна карточка-задача в Битриксе (`bitrix_task_id`).
- Связь: одна страна → много пиццерий. **Один дайджест в день на страну**, внутри — отдельный блок по каждой пиццерии. Всё уходит в один топик стройки.

Пример: чат «Кыргызстан», топик «Стройка» → бот раз в день шлёт дайджест с секциями по Бишкек 8, Бишкек 10, Бишкек 11.

## 4. Функциональные требования

1. Несколько раз в день — в фиксированные локальные часы `DIGEST_HOURS` (9/11/13/15/17/19 по таймзоне чата, §7, §12) — собирать дельту изменений по каждой отслеживаемой карточке (только новое с прошлого запуска); есть изменения — шлём, нет — молчим.
2. Отслеживать: новые комментарии (текст + автор + вложения) из чата задачи, изменения чек-листа, смену статуса задачи, дедлайна.
3. Формировать через LLM человеческий дайджест: выжимка обсуждения и выводы (а не дословный пересказ), статус чек-листа, строки про файлы.
4. Публиковать дайджест строго в заданный топик стройки.
5. Партнёры сами добавляют/убирают карточки и меняют язык/время через команды бота.
6. Бот получает из чата **только команды и reply на свои сообщения** (privacy mode Telegram остаётся включённым, §14) — обычная переписка партнёров через бота не проходит вовсе, не логируется и не хранится.
7. **Пустой день — бот молчит.** Если за день ни по одной карточке страны нет изменений, дайджест не отправляется и LLM не вызывается. После 7 дней тишины подряд — один короткий недельный пинг («по стройкам без изменений с {дата}»), чтобы партнёры видели, что бот жив.
8. Мультиязычность (минимум ru/en, в перспективе es, sl и др.).
9. Промпт LLM выносится наружу и меняется без правки кода.
10. (Фаза 3) Отчёт по требованию: команда `/report` — дайджест в моменте, не дожидаясь дневного расписания.

## 5. Команды бота

Команды вводятся прямо в топике стройки. Бот из сообщения с командой автоматически берёт `chat_id` и `message_thread_id` — отдельно ID топика вводить не нужно.

Правила захвата `thread_id`: брать `message_thread_id` **только если** `message.is_topic_message == true`. Иначе (обычная группа, General-топик) сохранять NULL и при отправке параметр опускать. `message_thread_id` из reply-треда — это id треда ответов, не топика; **не сохранять никогда** (иначе отправка упадёт с «message thread not found»).

При первой команде в топике бот сам создаёт запись чата (upsert по `telegram_chat_id + message_thread_id`); поле `country` заполняется названием супергруппы из Telegram (`getChat().title` — де-факто это и есть страна: «Кыргызстан»). `repo.upsert_chat` возвращает `(ChatRow, created)` — `created=True`, только если запись заведена именно этим вызовом (различение через `xmax = 0` в `RETURNING`). При `created=True` бот **тихо** пробует автоопределить таймзону чата: `resolve_tz(title чата)` (см. `src/telegram/tz_aliases.py`, ниже) — резолвится → `digest_time` остаётся дефолтным `09:00`, но `timezone` сразу выставляется найденной (без отдельного ответа партнёру, таймзона видна позже через `/time`); не резолвится (например тестовый чат `group_za_test`) — чат остаётся на дефолтной `UTC`, как и раньше. Партнёр Telegram не отдаёт таймзону пользователя напрямую, но домен бота ограничен странами сети — название супергруппы почти всегда и есть страна/город, так что автоопределение по нему работает в подавляющем большинстве случаев.

- `/add <task_id ИЛИ ссылка>` — добавить карточку к отслеживанию в этом топике. Карточек в Битриксе
  миллион, поиск по названию не годится — принимаем либо голый ID (`/add 8017`), либо ссылку на
  карточку, скопированную из браузера (`https://b24.dodoteam.ru/company/personal/user/1650/tasks/
  task/view/42103/`, бывает и `.../workgroups/group/25/tasks/task/view/42103/`): ID вытаскивается
  регэкспом `/tasks/task/view/(\d+)`, префикс пути и хвост (`?commentId=1#com1`) значения не имеют.
  - Бот валидирует ID через `tasks.task.get`: задача не найдена / нет доступа → локализованный ответ «задача не найдена или нет доступа»; уже отслеживается → «уже отслеживается».
  - Успех → подтверждение «Отслеживаю: Бишкек 8 (#8017)»; `alias` заполняется **автоматически названием задачи**.
  - Курсор инициализируется **текущими максимальными** `history_id` и `message_id` чата задачи — отслеживание идёт «с этого момента», первый дайджест не вываливает историю стройки за прошлые месяцы. (Стартовое саммари всей истории — отдельная возможная фича, не MVP.) Если у задачи нет чата (старая карточка) — `last_message_id = 0`, комментарии по ней в MVP не собираются (см. fallback в §13).
  - **Подзадачи подхватываются автоматически** — вручную вызывать `/add` на каждую не нужно. На каждом прогоне дайджеста, до сбора дельты, бот сканирует подзадачи РУЧНЫХ карточек чата (`tasks.task.list` с `filter: {"PARENT_ID": <id>}`) и заводит новые как отдельные карточки: `alias = "<alias родителя> / <название подзадачи>"`, `cards.auto_from` = id родителя, курсоры «с этого момента» — подробности дискавери в §7.
  - **Автонастройка чата из карточки при первом /add** (владелец, дизайн зафиксирован): если чат ещё не был настроен вручную (`chats.auto_configured = FALSE`, миграция `0005_auto_configured.sql`, §12), после успешного `add_card` бот **одним** LLM structured-output вызовом (`llm.detect_card_locale`, `src/digest/llm.py`) определяет по названию карточки и последним ~10 комментариям обсуждения: (1) **язык** — `ru`, если ТЕКСТ комментариев обсуждения преимущественно на русском, иначе `en` (только эти два значения, см. §10; название карточки и имена авторов для языка не учитываются — оба часто латиницей даже у русскоязычной команды, живой кейс — карточка «Podgorica-2» с авторами «Cheredanova Kristina» / «Юрьев Вадим» при обсуждении на русском); (2) **IANA-таймзону** города, упомянутого в названии карточки — единственного источника для этого поля (например «Podgorica-2» → `Europe/Podgorica`), либо пусто, если город неясен. Успешный детект тихо применяет язык (`set_chat_language`) и, если таймзона резолвилась и прошла валидацию (`tz_aliases.is_valid_zone` — точная сверка с `available_timezones()`, LLM отдаёт готовую IANA-строку, а не человеческое название), время `09:00` в этой таймзоне (`set_chat_time`) — без дополнительных сообщений партнёру, ответ `/add` не меняется. `auto_configured` выставляется в `TRUE` ТОЛЬКО при полном успехе детекта и применения (внутри одного try/except в `_auto_configure_from_card`), чтобы не гонять детект на каждой следующей карточке того же чата; при любой ошибке (LLM/сеть/БД) флаг остаётся `FALSE` — см. «Тихая деградация» ниже. **Ручная настройка всегда побеждает**: `/lang` и `/time` сразу ставят `auto_configured = TRUE` при успешном применении, и автонастройка из карточки для этого чата больше никогда не запускается. **Тихая деградация** (владелец): LLM недоступен после ретраев, вернул мусор, сеть или БД подвели — весь блок детекта обёрнут в try/except, `/add` не падает и не тормозит сверх обычного (~1–2 с на детект), настройки чата не меняются, `auto_configured` остаётся `FALSE` — бот попробует снова на следующей подключаемой карточке. Комментарии для детекта собираются той же веткой «есть чат задачи / нет чата», что и `collector.collect_card_overview` (§7 п.2): новая карточка — `im.dialog.messages.get`, старая — `task.commentitem.getlist` со снятым BB-кодом (`strip_bbcode`).
- `/remove <task_id>` — снять карточку с отслеживания (`active = false`; история связки сохраняется). Если снимаемая карточка **РУЧНАЯ**, заодно деактивируются и её авто-подхваченные подзадачи (`auto_from = task_id`) в этом чате — партнёр убирает стройку целиком, а не только шапку. Повторный `/add` реактивирует карточку (и превращает её обратно в ручную, если она была авто-подхваченной) и заново инициализирует курсор текущим максимумом. Неотслеживаемый ID → «эта карточка не отслеживается».
- `/list` — показать карточки, отслеживаемые в этом топике. Авто-подхваченные подзадачи помечаются «↳» перед alias вместо обычного «•» — видно, что карточка появилась сама, а не через `/add`.
- `/lang <code>` — язык дайджеста для этого чата (например `/lang ru`, `/lang en`). Неизвестный формат кода → подсказка с примерами.
- `/time <HH:MM> <город, страна ИЛИ IANA-таймзона>` — время дневного дайджеста этой страны, например `/time 09:00 Белград`, `/time 09:00 Belgrade` или `/time 09:00 Europe/Belgrade` — все три эквивалентны. Второй+ аргумент резолвится через `resolve_tz` (`src/telegram/tz_aliases.py`): сперва как есть — точный IANA-идентификатор (сверка с `zoneinfo.available_timezones()`, регистрозависимо); не совпало — по словарю алиасов городов/стран сети Dodo International, регистронезависимо (ru и en, минимум по паре алиасов на страну — см. `TZ_ALIASES`). Время валидируется форматом HH:MM. Ничего не резолвилось (ни время, ни таймзона) → локализованная подсказка с примером, настройки не меняются. Без второго аргумента меняется только время — но если у чата всё ещё дефолтная `UTC`, бот просит указать город/таймзону явно (иначе партнёр из Бишкека молча получит «09:00 UTC» = 15:00 местных). Фидбек владельца (скриншот): партнёр ответил на time-prompt «14:49 белград» и получил подсказку «Использование: …» — раньше принимался только голый IANA-идентификатор; теперь принимается человеческое название города/страны.
- **Голая команда без аргументов = диалог, не usage-подсказка.** `/add`, `/time`, `/lang`, `/remove` без аргументов открывают тот же диалоговый флоу, что и кнопки `/menu` (prompt-реплай для add/time, клавиатура для lang/remove) — вместо текста «Использование: …». Тот текст остаётся, но только на **непустые невалидные** аргументы (`/time 9:99`, `/add фигня`).
- `/report [<task_id ИЛИ ссылка>]` — **реализовано**: дайджест в моменте по этому топику (тот же пайплайн §7, только по запросу; курсоры двигаются так же, но `last_digest_date` **не** трогается — дневной дайджест выходит по расписанию; если `/report` уже съел дельту, дневной может оказаться пустым и не отправиться, §7 п.5). Без аргумента открывает выбор карточки — то же диалоговое меню, что и кнопка «📊 Отчёт сейчас» (см. `/menu` ниже): «По всем» гонит отчёт по всему топику как раньше, кнопка конкретной карточки — точечный отчёт **только по ней** (`process_chat(..., only_task_id=<id>)`): дискавери подзадач при точечном отчёте пропускается целиком (не нужен для быстрого прогона по одной карточке), блоки «изменений нет» соседних карточек в сообщение не попадают. С аргументом (голый ID или ссылка на карточку, тот же `_parse_task_ref`, что у `/add`) отчёт по этой карточке запускается сразу, без меню выбора; если карточка не отслеживается в этом топике — ответ «эта карточка не отслеживается в этом топике» (`report_unknown_card`), по аналогии с `/remove` на неотслеживаемый ID.
  - **В выборе карточки — только РУЧНЫЕ карточки.** Фидбек владельца (скриншот): авто-подхваченная подзадача («Belgrade-2 / Доработки Dine-in») не должна быть отдельным пунктом выбора — она подразумевается родителем. Кнопки меню выбора строятся только по карточкам с `auto_from IS NULL`; авто-подхваченные подзадачи в списке не показываются вовсе. Точечный отчёт по РОДИТЕЛЮ (кнопка родителя или `/report <id/ссылка родителя>`) автоматически включает и его авто-подхваченные подзадачи: `only_task_id` матчит карточку, если `bitrix_task_id == only_task_id` **ИЛИ** `auto_from == only_task_id` — блоки родителя и всех его детей едут в одном отчёте, курсоры всех сдвигаются при успешной отправке. Адресация НАПРЯМУЮ на авто-ребёнка (только через `/report <id/ссылка подзадачи>` — своей кнопки в меню выбора у него нет) остаётся точечной: матчит только сам себя, ни родителя, ни братьев не подтягивает (условие симметрично — `auto_from` ребёнка не совпадает с его же `only_task_id`).
  - **Отчёт по запросу всегда с содержимым.** Фидбек владельца: «если человек нажал что нужен дайджест — значит надо дайджест» — явный запрос никогда не отвечает голым «изменений нет» по карточке. Все report-пути (кнопки `m:report:*`, `/report`, `scripts/force_report.py`) вызывают `process_chat(..., overview_on_empty=True)` (§9.1): карточка без НОВЫХ изменений получает не короткую строку, а сводку **текущего состояния** — `collector.collect_card_overview` берёт последние комментарии независимо от курсора, LLM пишет сводку по `prompts/overview.txt` с системным нотисом `report_no_new`/`report_no_new_never` (та же дата, что у `report_empty` ниже). Курсоры такой карточки не двигаются. Ежедневный тик этого не делает (`overview_on_empty=False` по умолчанию) — молчание при полностью пустом чате остаётся фичей (§7 п.5).
  - **«Изменений нет» — с датой (последний fallback).** Если карточке буквально нечего показать даже в overview-режиме (её никогда не обсуждали) — она получает не пустой блок, а строку «С последнего дайджеста (ДД.ММ ЧЧ:ММ) изменений нет» (дата — `chats.last_posted_at` **в таймзоне чата**; `last_posted_at IS NULL` → «С момента подключения изменений нет», без даты-заглушки). Тот же текст на уровне ЧАТА — последний fallback `menu.run_report`, если охват отчёта вообще не дал ни одной карточки (`posted=False`, например точечный отчёт по уже снятой карточке).
- `/menu` — **реализовано**: панель с inline-кнопками (добавить/убрать карточку, отчёт сейчас, время, язык). Callback-кнопки не зависят от privacy mode и адресации; ввод номера карточки/времени — reply на prompt-сообщение бота (reply проходит privacy mode; действие определяется точным совпадением текста prompt'а). Права нажавшего в restricted-чатах проверяются по `callback.from_user` (§6). Кнопка «📊 Отчёт сейчас» **не** гонит отчёт сама по себе — сперва показывает выбор карточки (по всем / по каждой АКТИВНОЙ РУЧНОЙ карточке / отмена — авто-подхваченные подзадачи в списке не значатся), тем же экраном, что и голый `/report`.
- В группах команды принимаются только адресно (`/add@dodo_constr_bot 42103`) — в чате могут жить другие боты со своей `/add`; кнопки меню адресации не требуют.

## 6. Права доступа

- По умолчанию команды доступны **всем** участникам чата (партнёрские команды — взрослые люди, справятся).
- В схеме заложен флаг `restricted` на уровне чата. Значение по умолчанию — «открыто». Если по какой-то стране понадобится ограничить, флаг переключается, и команды начинают слушаться только вайтлиста (`chat_admins`). **Код при этом не меняется.**
- Для MVP переключение `restricted` и наполнение `chat_admins` — **руками в БД** (SQL от владельца бота). Это осознанное решение: команды управления вайтлистом появятся, только если ограничение реально понадобится.

## 7. Как работает дневная дельта (ядро Фазы 1)

**Планировщик (слоты по местному времени).** Джоба тикает каждые `SCHEDULER_TICK_MINUTES` (5 минут). На каждом тике по каждому активному чату проверяется `is_digest_due`: локальное время (`timezone` чата, `safe_zoneinfo` с UTC-fallback) сравнивается со слотами `DIGEST_HOURS` = (9, 11, 13, 15, 17, 19). Берётся последний наступивший сегодня слот; если `last_run_at IS NULL` ИЛИ `last_run_at` раньше начала этого слота — запускается сбор по карточкам чата, а `last_run_at` обновляется текущим timestamp'ом (`mark_digest_run`). До 9:00 и после 19:00 (ночью) — не due. `digest_time` в схеме остаётся (команда `/time` его пишет), но на расписание не влияет — слоты фиксированы; `timezone` же критична, именно она определяет момент слотов. Молчание при отсутствии изменений (§7 п.5) само глушит поток на пустых слотах. Прогоны не накладываются: джоба в один поток (APScheduler `max_instances=1`, §11). Catch-up: после простоя сервера первый тик увидит непройденный слот и догонит (один раз, накопленная дельта уедет вся).

**Дискавери подзадач** (`scheduler._discover_subtasks`, перед сбором дельты): для каждой активной **РУЧНОЙ** карточки чата (`cards.auto_from IS NULL` — авто-подхваченные карточки сами родителями не становятся, иначе подзадачи подзадач дискаверились бы рекурсивно; уровень вложенности ровно один) бот запрашивает её подзадачи (`tasks.task.list` с `filter: {"PARENT_ID": <id>}`, scope `task`; пагинация не нужна — подзадач на карточке единицы). Каждая подзадача, которой ещё нет среди карточек этого чата — **ни активной, ни деактивированной** (снятую партнёром вручную карточку дискавери не реанимирует, см. `repo.card_exists`), — заводится как отдельная карточка: `alias = "<alias родителя> / <название подзадачи>"`, `cards.auto_from` = `bitrix_task_id` родителя, курсоры инициализируются «с этого момента», как у обычного `/add` (`get_latest_history_id`; `last_message_id = 0` — задачи этого портала без чатов, см. §13, отдельным вызовом за `chatId` подзадачи дискавери не дорожает; `get_latest_comment_id` с деградацией в `0` при ошибке API). Сбой дискавери по одному родителю логируется и попадает в `ADMIN_CHAT_ID`-сводку, но не роняет прогон чата — та же изоляция «try/except на один элемент», что у сбора дельты ниже (п.9).

**По каждой карточке чата:**

1. **История:** `tasks.task.history.list`. Внимание: фильтра «новее ID» у метода **нет** (filter умеет только тип события) — серверного среза «после курсора» не существует. Дельта режется на клиенте: читаем страницами (50/страницу, порядок по умолчанию desc), останавливаемся, как только id записи ≤ `last_history_id`. Из истории берём: изменения чек-листа (`CHECKLIST_ITEM_CREATE/RENAME/REMOVE/CHECK/UNCHECK`), смену статуса, дедлайна и т.п.
2. **Комментарии** — путь выбирается по наличию чата у задачи (`tasks.task.get` c `select: ["chat.id"]`):
   - **есть чат** (новая карточка): `im.dialog.messages.get` (`DIALOG_ID = "chatN"`, `FIRST_ID = last_message_id` — курсор встроен, `LIMIT ≤ 50`; вложения в блоке `files`). Системные сообщения (признак system/`author_id = 0`) отфильтровываются — иначе задублируют события истории из п.1.
   - **нет чата** (старая карточка — **текущая реальность портала**, смоук 2026-07-23): `task.commentitem.getlist` (deprecated, но живое) — клиентская резка по курсору `last_comment_id` (`int(ID) > cursor`), BB-коды (`[USER=…]`, `[URL=…]`, `[B]` и т.п. — whitelist реальных тегов) снимаются перед LLM; вложения из `ATTACHED_OBJECTS` идут со ссылкой на **комментарий-источник** (`disk.file.get` на сам файл отдаёт ACCESS_DENIED, поэтому ссылка ведёт не на файл, а на комментарий — `links.comment_url`, подробности в §8; `DOWNLOAD_URL`/`VIEW_URL` содержат токен вебхука — не публикуются никогда).
3. **Чек-лист, текущее состояние:** `task.checklistitem.getlist` (посчитать выполнено/всего по `IS_COMPLETE`). Чек-листы Битрикса иерархичны: пункты с `PARENT_ID` отсутствующим/`None`/`"0"`/`0` — этапы (корни), у них есть дочерние пункты. Владельцы чек-листа отмечают дочерние пункты, а не корневую галочку этапа — статус этапа определяется **только по его детям** (`get_checklist_summary`, `src/bitrix/methods.py`). Из этого системно (без LLM) собирается вторая строка шапки карточки в дайджесте: первый по `SORT_INDEX` этап с незакрытыми детьми, либо «все этапы закрыты», либо плоский счётчик `done/total`, если у чек-листа вообще нет иерархии (§9).
4. **Файлы:** id вложения → `disk.file.get` → постоянный `DETAIL_URL` (подробности и запреты — §8).
5. **Пустая дельта:** если по всем карточкам чата ничего нового — LLM не вызывается, ничего не отправляется, `last_digest_date` помечается (день обработан). Если по части карточек пусто, а по части нет — дайджест уходит; пустые пиццерии получают одну строку «изменений нет» из locale-файла (тоже без вызова LLM).
6. **LLM:** сырьё по пиццерии (обсуждение + изменения) → OpenAI. Ретраи: 2–3 попытки с экспоненциальным backoff. Финальный отказ → **fallback**: отправить сырой структурированный список изменений (авторы + первые строки комментариев, чек-лист N/M, файлы со ссылками) с пометкой «краткая версия без выжимки» + алерт в `ADMIN_CHAT_ID`. Дайджест деградирует, но не исчезает молча.
   **Кэш LLM-выжимок** (таблица `llm_cache`, миграция `0004_llm_cache.sql`, §12) — повторные «Отчёт сейчас» по тем же данным не должны каждый раз дёргать OpenAI, а сбой провайдера (например простой с 500) не должен ронять уже однажды посчитанный отчёт в fallback. Ключ — `material_hash(prompt)` (`src/digest/llm.py`, sha256 финального промпта): промпт детерминированно включает всё сырьё (комментарии, изменения, чек-лист, язык, шаблон), а `{date}` в нём меняется каждые сутки — значит и без TTL кэш живёт не дольше дня; `TTL 24h` в `repo.get_cached_llm` — вторая, независимая от содержимого промпта страховка. Точка входа — `scheduler._summarize_cached` (общая для дайджеста и overview-сводки, §5): хэш есть в кэше и не протух → выжимка отдаётся без обращения к OpenAI; нет → LLM вызывается как обычно, успешный результат кладётся в кэш (`repo.put_cached_llm`, UPSERT по `material_hash` + попутная ленивая очистка записей старше 48h). `LlmUnavailable` при пустом кэше — как раньше: fallback-рендер + алерт. Сбой самого кэша (БД недоступна) не должен ломать генерацию — `get_cached_llm`/`put_cached_llm` обёрнуты в try/except с `log.warning`, дайджест продолжает работать без кэша. Bitrix при этом дёргается всегда — это дешёво и остаётся единственным источником инвалидации по существу.
7. **Отправка:** **одно сообщение на чат** (владелец, дизайн «дайджест одним сообщением»): блоки всех пиццерий чата — и с изменениями, и `no_changes_line`-строки, и авто-подхваченные подзадачи — склеиваются через `render.chunk_blocks` в текст, разделитель между блоками — пустая строка. Если суммарная длина укладывается в лимит (§14) — уходит одно сообщение. При переполнении — **сплит на минимальное число сообщений по границам блоков**: блок карточки никогда не рвётся пополам; если один блок сам по себе длиннее лимита — он и раньше срезался `render.clip` на уровне рендера, здесь получает собственный чанк без дальнейшей резки. Чанки отправляются последовательно в топик (`scheduler.process_chat`, фазы: рендер блоков → `chunk_blocks` → отправка).
8. **Курсоры:** у каждой связки (карточка, чат) свой курсор (`last_history_id`, `last_message_id`). Granularity сдвига курсора — **чанк, а не карточка**: курсор двигается **только после подтверждённой успешной отправки** того сообщения (чанка), в которое вошёл блок этой карточки — семантика at-least-once: редкий дубль при падении между отправкой и записью курсора приемлем, молчаливая потеря дельты — нет. Сбой отправки чанка (`result.ok=False`) **не двигает курсоры ни одной из карточек этого чанка** — ошибка в сводке `ADMIN_CHAT_ID` перечисляет их `task_id` (например, «не отправлен чанк дайджеста (#8017, #8018)»); курсоры карточек из других, успешно отправленных чанков того же прогона, это не задевает. Внутри уже успешно отправленного чанка запись курсора каждой карточки обёрнута в **свой** try/except: сбой `advance_cursor` одной карточки не должен глушить запись курсоров остальных карточек того же чанка (иначе их дельта уехала бы завтра повторно — дубль в дайджесте, — хотя сообщение было доставлено); такой сбой тоже попадает в сводку `ADMIN_CHAT_ID` с `task_id` карточки. Особый случай — `forbidden` (бот выкинут из чата): чат деактивируется и оставшиеся чанки этого прогона не отправляются вовсе (курсоры уже отправленных чанков остаются сдвинутыми). Кэшировать в рамках прогона можно **только сырые страницы** истории/сообщений по task_id (читая от минимального курсора среди чатов этой карточки); резать дельту — по курсору каждого чата отдельно: у чатов разные стартовые точки, и чужой срез молча теряет или дублирует события.
9. **Завершение прогона по чату:** независимо от частичных сбоев по отдельным карточкам выставляется `last_digest_date` (текущая локальная дата), а если отправлено хоть одно содержательное сообщение (включая fallback) — обновляется `last_posted_at`. Упавшие карточки до завтра не ретраятся: их курсоры не сдвинуты, дельта не потеряна и уедет со следующим дайджестом, а сбой попадает в сводку `ADMIN_CHAT_ID`. Это исключает 5-минутный ретрай-спам по чату со стабильной ошибкой.

**Недельный пинг:** если у чата есть активные карточки и ≥ `WEEKLY_PING_DAYS` (7) дней не было ни содержательного сообщения (`last_posted_at`), ни предыдущего пинга (`last_ping_at`; для нового чата опора — `created_at`), то на тике его `digest_time` бот шлёт одну строку «по стройкам без изменений с {дата}», где `{дата}` = `last_posted_at` (начало тишины; если NULL — дата подключения чата). Пинг обновляет `last_ping_at`, но **не** `last_posted_at` — дата начала тишины не дрейфует от пинга к пингу.

> Шаг 6 — это тот «слой над conversations»: LLM читает переписку и делает выводы, а не пересказывает дословно.

## 8. Файлы

Идём простым путём — **не читаем содержимое**, а сигнализируем и даём ссылку:

- В дайджесте, там где упоминается **пиццерия** (заголовок секции) — ссылка на **карточку задачи**. Ни один REST-метод URL карточки не возвращает — бот конструирует его сам: хост портала (из `BITRIX_WEBHOOK_URL`) + `/company/personal/user/<user_id владельца вебхука>/tasks/task/view/<task_id>/`. Кликабельность проверяется на смоук-тесте Фазы 0 (§13).
- Там где упоминается **файл чата задачи** (новая карточка, `resolve_files`) — ссылка на **сам файл** (`DETAIL_URL`).
- Там где упоминается **файл комментария старой карточки** (fallback §13, `ATTACHED_OBJECTS`) — ссылка на **комментарий-источник** внутри карточки, а не на файл: `disk.file.get` по этим файлам отдаёт `ACCESS_DENIED` (смоук-тест, см. ниже), владелец утвердил линковать на комментарий вместо файла. Формат (`links.comment_url`): `<URL карточки>?commentId=<id>#com{id}`, где `<id>` — id комментария, несущего вложение (`parse.extract_comment_files` отдаёт пары «имя файла, id комментария»).

Важно про ссылки Битрикса:

- **`DETAIL_URL` возвращает только `disk.file.get`** — постоянная страница файла на портале, открывается после входа в Битрикс (у партнёров доступ есть). **Использовать её.** `disk.attachedObject.get` поле `DETAIL_URL` не отдаёт — он нужен только для маппинга вложения на файл (`OBJECT_ID`). Рабочая цепочка: `FILE_ID`/`OBJECT_ID` вложения → `disk.file.get` → `DETAIL_URL`.
- `DOWNLOAD_URL` из вложений партнёрам **не давать — вдвойне**: ссылка не только протухает, но при вызовах через входящий вебхук содержит **незатухающий токен вебхука** — опубликовать её значит слить секрет с полным доступом к API. Это касается и `urlDownload` из блока `files` чата задачи.
- Для файлов из чата задачи проверить на смоук-тесте Фазы 0, что их id резолвится через `disk.file.get` (см. §13).

**Рендер ссылки в тексте выжимки** (`render.card_message`): если LLM упомянула имя файла со ссылкой дословно в тексте — имя превращается в `<a href="...">` прямо там, инлайн, и 📎-блок внизу его не дублирует. Если файл со ссылкой не упомянут в тексте (или выжимки нет — fallback) — ссылка идёт в 📎-блоке, как и раньше. Файл без ссылки (совсем неопознанное вложение) в 📎-блоке показывается только именем.

Чтение содержимого PDF/картинок через OpenAI — опция на будущее (Фаза 4). Архитектурно оставить под неё место, но в MVP не включать. CAD-форматы (DWG/DXF) OpenAI напрямую не читает — если понадобится, потребуется конвертация.

## 9. Промпт LLM

Хранится **вне кода — файлом в репозитории** (`prompts/digest.txt`): версионирование даёт git, бот перечитывает файл при старте процесса. Меняешь текст промпта — код не трогаешь. (Таблица `prompts` в Postgres из MVP убрана — вернётся на Фазе 4, если понадобится править промпт без доступа к серверу; два канонических места хранения = гарантированный дрифт.)

Канонический текст живёт в `prompts/digest.txt` (эта цитата — зеркало для чтения, при правке файла обновлять и её):

```
Ты пишешь дневной апдейт по стройке пиццерии для партнёрского чата.
Язык апдейта: {language}. Тон — деловой, короткий, по делу. Не более ~250 слов.

Исходные данные (не выводи их как есть — это сырьё для выжимки):

Дата: {date}
Пиццерия: {pizzeria_name}
Чек-лист: {checklist_state}
Изменения задачи (статус, дедлайн, чек-лист):
{task_changes}

Обсуждение за день (автор -> сообщение):
{comments}

Файлы за день: {files}

Собери апдейт из секций — строго в этом порядке, с этими эмодзи.
Заголовки секций переведи на язык апдейта. Секцию, для которой нет
содержания, полностью опусти — не пиши «нет» или «—».

✅ Что изменилось
• 1–5 пунктов: решения, согласования, завершённые шаги. Выводы, а не пересказ.

⚠️ Требует внимания
• Открытые вопросы, несостыковки, ожидания ответов.

🚧 Блокеры
• Только то, что реально останавливает работу.

📌 Следующие действия
• Формат «Имя: действие». Только если из переписки ЯВНО следует, кто и что
  делает дальше. Если не уверен в исполнителе или действии — опусти пункт
  или всю секцию. Ничего не придумывай.

Правила:
- Если у сообщения указаны [вложения: …] — упомяни эти файлы в пункте, к
  которому они относятся, дословно теми же именами: (вложения: имя1, имя2).
  Отдельный список файлов не делай — его добавит система.
- Если материала много, приоритизируй: блокеры → решения → следующие действия →
  прочее. Лучше опустить мелочи, чем сжать блокер до неузнаваемости.
  В насыщенный день допустимо до ~350 слов, но не больше.
- Заголовок с названием пиццерии не пиши — его добавит система.
- Не выдумывай фактов, имён и сроков. Всё, что не следует из данных, — опускай.
```

Плейсхолдеры `{...}` подставляет бот. `{comments}` — строки «автор -> текст», и если у сообщения/комментария есть вложения — с постфиксом `[вложения: имя1, имя2]` (имена берутся из `files[*].name` чата задачи новой карточки или `ATTACHED_OBJECTS[*].NAME` своего комментария старой карточки); так LLM упоминает файлы в контексте темы обсуждения, а не безликим списком в конце. На дневном тике вызов LLM происходит **только при непустой дельте** (§7 п.5). Вывод LLM ограничивается `max_tokens` и прогоняется через `html.escape`; ссылку на карточку система подставляет в заголовок, а ссылки на файлы (`DETAIL_URL` новой карточки или пермалинк комментария старой, §8) — либо инлайн прямо в тексте выжимки (если LLM упомянула имя файла дословно), либо отдельным 📎-блоком внизу, если не упомянула (LLM ссылки не выдумывает — только имена).

Шапка карточки в дайджесте — тоже системная, не LLM: первая строка — название пиццерии со ссылкой на карточку (`🏗 <b><a href="...">alias</a></b>`), вторая — статус чек-листа (`get_checklist_summary`, §7 п.3): текущий незакрытый этап и счётчик, «все этапы закрыты», либо плоский `done/total` без иерархии. Строка идёт в обоих режимах — и при живой LLM-выжимке, и в fallback без неё.

### 9.1 Второй промпт-файл — сводка «текущее состояние» (`prompts/overview.txt`)

Фидбек владельца: «если человек нажал что нужен дайджест — значит надо дайджест» — явный запрос отчёта (кнопки `m:report:*`, `/report`, `scripts/force_report.py`; всё, что зовёт `process_chat` с `mark_run=False`) не должен отвечать голым «изменений нет» карточке, по которой просто не случилось ничего НОВОГО с прошлого прогона. Второй промпт-файл хранится и версионируется так же, как `prompts/digest.txt` — рядом, вне кода, перечитывается при старте процесса:

```
Ты пишешь сводку ТЕКУЩЕГО состояния стройки пиццерии по запросу партнёра.
Язык: {language}. Тон — деловой, короткий. Не более ~120 слов.

Новых изменений нет — задача: напомнить, где стройка сейчас, по последним
комментариям и чек-листу.

Дата: {date}
Пиццерия: {pizzeria_name}
Чек-лист: {checklist_state}

Последние комментарии (автор -> сообщение):
{comments}

Сделай секцию:
📍 Где мы сейчас
• 2-4 пункта: ключевые темы последних обсуждений, принятые решения, открытые вопросы.
Правила: заголовок секции переведи на язык сводки; файлы упоминай именами из [вложения: …];
ничего не выдумывай; заголовок с названием пиццерии не пиши — его добавит система.
```

Отличия от `prompts/digest.txt`: нет `{task_changes}`/`{files}` — сводка не про то, что изменилось, а про то, где стройка сейчас; `{comments}` собирает **последние k (по умолчанию 5) комментариев независимо от курсора** (`collector.collect_card_overview`, а не `collect_card_delta`) — специально, чтобы напомнить контекст, даже если он не «новый». Курсоры при этом **не двигаются**: `collect_card_overview` возвращает `new_*_id` как есть из переданного `cursor` — сдвиг курсора в report-пути на этих значениях оказывается no-op, безопасно повторяемым.

`scheduler.process_chat(..., overview_on_empty: bool = False)` — все report-пути передают `True`. Карточка без новых изменений в этом режиме получает: шапку (как обычно) → системную строку-нотис `report_no_new`/`report_no_new_never` (та же дата, что у `report_empty`, см. §5) → строку чек-листа → LLM-сводку по `prompts/overview.txt` (fallback при недоступности LLM — сырой список последних комментариев, как и у обычного дайджеста) → 📎-файлы из этих же комментариев. Если и `collect_card_overview` не находит вообще ничего (карточку никогда не обсуждали) — карточка получает не пустой блок, а строку `report_empty`/`report_empty_never` (с шапкой, чтобы в многокарточном отчёте было видно, к какой карточке относится) — LLM не вызывается. Ежедневный тик (`overview_on_empty=False`, дефолт) не меняется: полностью пустой чат по-прежнему молчит (§7 п.5).

## 10. Языки — два слоя, одна настройка

- **Язык дайджеста** (что бот пишет в топик): поле `digest_language` чата, подставляется в `{language}` промпта. Новый язык не требует ничего — LLM просто пишет на нём. Управляется командой `/lang`.
- **Язык интерфейса бота** (ответы на команды): locale-файлы (`ru.json`, `en.json`, …). Новый язык = один файл перевода.
- Для MVP оба слоя управляются **одним полем** `digest_language`: интерфейс использует locale-файл этого языка, а если файла нет (например `sl` для дайджеста есть, `sl.json` ещё не написан) — fallback на `en`. Отдельная колонка `interface_language` появится, только если слои реально разойдутся.
- **Автонастройка при первом /add** (§5): `digest_language` может выставиться не только через `/lang`, но и автоматически — LLM-детект (`llm.detect_card_locale`) читает обсуждение карточки и определяет `ru` (обсуждение преимущественно русское) либо `en` (любой другой язык — детект намеренно бинарный, третьих значений не бывает). Ручной `/lang` в любой момент переопределяет автоопределённое значение и дальше уже сам ничем не перебивается (`auto_configured`, §12).

Пример: Кыргызстан получает апдейты на русском, Словения — на словенском (ответы на команды — на английском, пока нет `sl.json`), код один.

- **Хостинг MVP — домашний сервер MUSPELHEIM** (Windows + Docker Desktop, постоянно включён): машина как раз настроена под TG-ботов на long polling — Docker, Postgres и ночные бэкапы уже есть. Проект — `C:\projects\construction_bot` копией из `C:\projects\_template`. Контейнер Postgres пометить `backup.pgdump=true` — тогда он попадает в штатный ночной автобэкап (03:30, ретеншн 14 дней). После проверки MVP — переезд на серверы компании (Фаза 4).
- **Сервис на Python**: `aiogram` 3.x (Telegram, long polling) + `httpx` (Битрикс) + `openai`.
- **Postgres 15+** — конфиг связок и курсоры дельты (в §12 используется `UNIQUE NULLS NOT DISTINCT`).
- **Планировщик** — APScheduler `AsyncIOScheduler` в том же event loop, что и polling (один процесс, без cron). Тик каждые 5 минут, per-chat время — §7; `coalesce=true` от накопления пропущенных тиков, `max_instances=1` — прогоны не накладываются (при 2 rps Битрикса полный прогон может длиться дольше тика).
- **Один polling-инстанс на токен**: два одновременно работающих процесса дадут конфликт `getUpdates`, и команды начнут теряться. При переезде на серверы компании — сначала остановить старый процесс, потом запускать новый.
- **Обработка ошибок:**
  - *Telegram:* `429 Too Many Requests` → экспоненциальный backoff по `retry_after` (aiogram кидает `TelegramRetryAfter`); `migrate_to_chat_id` → молчаливая смена chat_id при апгрейде группы до супергруппы, ловить (`TelegramMigrateToChat`) и обновлять сохранённый ID; «message is too long» при отправке цельного сообщения чата возникать не должно — страховка `render.chunk_blocks` сплитует по границам блоков **до** отправки (§7 п.7), а `render.clip` режет отдельный блок-переросток по границе строки, не разрывая теги; бот выкинут из чата — событие `my_chat_member` (kicked/left) или `TelegramForbiddenError` при отправке → `chats.active = false` + алерт в `ADMIN_CHAT_ID` (планировщик не долбится в мёртвый чат до ручной реактивации).
  - *Битрикс:* троттлинг клиента ≤ 2 rps (leaky bucket облака, порог блокировки 50); HTTP `503 QUERY_LIMIT_EXCEEDED` → retry с backoff; `batch` до 50 команд = 1 обращение к лимиту — использовать для опроса 50–80 задач.
  - *OpenAI:* ретраи + fallback на сырой список изменений (§7 п.6).
- **Наблюдаемость:** `ADMIN_CHAT_ID` (личка владельца или служебный чат, НЕ страновой) — после прогона с ошибками бот шлёт туда сводку. Ошибки классифицируются по маркерам строки (`scheduler._error_category`) и группируются: 🤖 LLM / 📋 Битрикс / ⚠️ Прочее — владелец сразу видит суть. Отдельный класс — **транзиентная связь с Telegram** (`scheduler._is_telegram_network_error`: маркеры `TelegramNetworkError`/`ClientConnectorError`/`Cannot connect to host api.telegram.org` и т.п.): это внешний сбой, не баг (бот ретраит, дельта не теряется), поэтому сырой стектрейс наружу не идёт и не спамит каждым прогоном — счётчик копится в `Deps.tg_net_pending` и отдаётся одним **суточным итогом** (`tg_net_summary_at`, интервал 24ч; первый инцидент — сразу, дальше троттл). Структурные логи по чату: сколько карточек, сколько событий, статус отправки.
- **Dry-run:** `DRY_RUN=true` — полный пайплайн (Битрикс + LLM), но вывод в stdout вместо Telegram. Для обкатки без спама в чаты.

## 12. Схема БД (Postgres 15+, черновик DDL)

```sql
CREATE TABLE chats (
    id                 BIGSERIAL PRIMARY KEY,
    country            TEXT,                          -- заполняется названием супергруппы при первом контакте
    telegram_chat_id   BIGINT NOT NULL,
    message_thread_id  BIGINT,                        -- NULL = чат без топиков / General
    digest_language    TEXT NOT NULL,                 -- при создании чата берётся из DEFAULT_LANGUAGE (.env)
    digest_time        TIME NOT NULL DEFAULT '09:00', -- локальное время страны
    timezone           TEXT NOT NULL DEFAULT 'UTC',   -- IANA, напр. 'Asia/Bishkek'
    last_digest_date   DATE,                          -- дедуп дневного прогона (локальная дата чата)
    last_posted_at     TIMESTAMPTZ,                   -- последний содержательный дайджест (пинг его НЕ двигает)
    last_ping_at       TIMESTAMPTZ,                   -- последний недельный пинг
    restricted         BOOLEAN NOT NULL DEFAULT FALSE,
    active             BOOLEAN NOT NULL DEFAULT TRUE, -- false = бот удалён из чата / чат выключен вручную
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    auto_configured    BOOLEAN NOT NULL DEFAULT FALSE, -- FALSE = следующий /add ещё может автонастроить язык+
                                                        -- таймзону из карточки (§5); TRUE ставит ручной /lang
                                                        -- или /time сразу, либо детект из карточки, но только
                                                        -- при ПОЛНОМ успехе (ошибка оставляет FALSE) —
                                                        -- миграция 0005_auto_configured.sql
    UNIQUE NULLS NOT DISTINCT (telegram_chat_id, message_thread_id)
);

CREATE TABLE cards (
    id              BIGSERIAL PRIMARY KEY,
    bitrix_task_id  BIGINT NOT NULL,
    chat_id         BIGINT NOT NULL REFERENCES chats(id) ON DELETE CASCADE,
    alias           TEXT,                          -- автоматически = название задачи при /add
    added_by        BIGINT,                        -- telegram user id
    active          BOOLEAN NOT NULL DEFAULT TRUE, -- /remove -> false; повторный /add реактивирует
    auto_from       BIGINT,                        -- NULL = добавлена вручную; иначе bitrix_task_id
                                                    -- родителя, от которого авто-подхвачена (§7, миграция 0003)
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (bitrix_task_id, chat_id)
);

CREATE TABLE cursors (
    bitrix_task_id  BIGINT NOT NULL,
    chat_id         BIGINT NOT NULL,
    last_history_id BIGINT NOT NULL,               -- init текущим max при /add
    last_message_id BIGINT NOT NULL,               -- курсор чата задачи (FIRST_ID); 0 = у задачи нет чата (§5, §13)
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (bitrix_task_id, chat_id),
    FOREIGN KEY (bitrix_task_id, chat_id)
        REFERENCES cards (bitrix_task_id, chat_id) ON DELETE CASCADE
);

CREATE TABLE chat_admins (
    chat_id          BIGINT NOT NULL REFERENCES chats(id) ON DELETE CASCADE,
    telegram_user_id BIGINT NOT NULL,
    PRIMARY KEY (chat_id, telegram_user_id)
);

CREATE TABLE llm_cache (                          -- миграция 0004_llm_cache.sql (§7, кэш LLM-выжимок)
    material_hash TEXT PRIMARY KEY,               -- sha256 финального промпта (src.digest.llm.material_hash)
    text          TEXT NOT NULL,                  -- готовая выжимка LLM
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()  -- TTL 24h читается отсюда; строки старше 48h чистятся лениво
);
```

Почему так:

- `UNIQUE NULLS NOT DISTINCT` — иначе два ряда одного чата с `message_thread_id = NULL` оба вставятся (в Postgres NULL ≠ NULL) и страна получит двойные дайджесты.
- Курсор — **per (карточка, чат)**, а не глобальный на задачу: если одну карточку отслеживают два чата (типовой случай — тестовый чат + боевой), глобальный курсор означает, что первый обработанный чат «съедает» дельту второго. Составной FK на `cards` каскадно чистит курсор при удалении связки.
- `cards.auto_from` (миграция `0003_auto_from.sql`) отличает авто-подхваченные подзадачи от ручных карточек — нужен и для дискавери (не сканировать авто-карточки как родителей, §7), и для каскадного `/remove` (снять карточку + её авто-детей, §5).
- Таблицы `prompts` в MVP нет — промпт живёт файлом (§9).
- `llm_cache` (миграция `0004_llm_cache.sql`, §7) хранит только готовый LLM-текст, а не сырьё дельты — ключ (`material_hash`) сам по себе уже хэш всего сырья, пересчитывать/хранить его отдельно незачем. PK на `material_hash` без отдельного FK на карточку/чат — кэш общий по содержимому: два чата с идентичной дельтой по совпадению получат один и тот же готовый текст без двух вызовов OpenAI.
- `chats.auto_configured` (миграция `0005_auto_configured.sql`, §5) — единый флаг «чат уже настроен, автодетект из карточки больше не нужен», общий для обоих путей: ручной (`/lang`, `/time` — ставят его сразу) и автоматический (детект по карточке при первом `/add` — ставит его в `TRUE` только при полном успехе детекта и применения; любая ошибка LLM/сети/БД оставляет флаг `FALSE`, и следующий `/add` этого чата повторит попытку). Один флаг, а не отдельные «язык настроен вручную» / «таймзона настроена вручную», потому что оба значения приходят ОДНИМ LLM-вызовом и всегда применяются вместе — раздельные флаги добавили бы состояния, которых на практике не бывает.

## 13. Битрикс24 — API

Доступ через **входящий вебхук** (URL вида `https://<portal>/rest/<user_id>/<token>/<method>`). Права: **задачи + диск + чаты (im)** — без `im` не прочитать комментарии новой карточки. Вызовы идут от имени пользователя-владельца вебхука: он должен видеть все отслеживаемые задачи (участник/наблюдатель/руководитель).

Нужные методы:

- `tasks.task.get` — карточка, статус, ответственный, дедлайн; через `select: ["chat.id"]` — id чата задачи; валидация `/add` (§5).
- `tasks.task.list` — с `filter: {"PARENT_ID": <id>}` (scope `task`) отдаёт подзадачи родителя (`result.tasks`); дискавери авто-подхвата (§7) — проверено живьём: у 42103 подзадача 73689. Пагинация не нужна — подзадач на карточке единицы.
- `tasks.task.history.list` — история изменений задачи (создание, `CHECKLIST_ITEM_*`, смена полей) с датой и автором. Фильтр — **только по типу события**, среза «новее ID» нет: дельта режется на клиенте (§7 п.1).
- `im.dialog.messages.get` — сообщения чата задачи (`DIALOG_ID = "chatN"`; `FIRST_ID` — курсор «сообщения новее ID», `LIMIT ≤ 50`; вложения в блоке `files`). **Основной источник комментариев** на новой карточке. Требует scope `im`.
- `task.commentitem.get` / `task.commentitem.getlist` — **deprecated с tasks 25.700.0, в новой карточке не работают.** Fallback для старых карточек — **вне схемы MVP**: решение после смоук-теста; если живые старые карточки реально встретятся, в `cursors` добавится nullable `last_comment_id` (id комментариев — другое пространство идентификаторов, чем сообщения чата).
- `task.checklistitem.getlist` — пункты чек-листа с состоянием `IS_COMPLETE`.
- `disk.attachedObject.get` — маппинг вложения на файл (`OBJECT_ID`); `disk.file.get` — параметры файла, в т.ч. постоянный `DETAIL_URL` (только этот метод его отдаёт).

**Смоук-тест Фазы 0 — прогнан 2026-07-23 на живой карточке 42103 (Belgrade-2), результаты:** (а) чата задачи НЕТ (`chatId` отсутствует) — карточки старого типа, комментарии через `task.commentitem.getlist` (314 шт., отвечает без пагинации); (б) `COMMENT` в `tasks.task.history.list` присутствует; (в) `disk.file.get` на файлы из комментариев — ACCESS_DENIED → файлы этой карточки в дайджесте без прямой ссылки на файл (см. §8 — итоговое решение: ссылка на комментарий-источник, а не голое имя); (г) URL карточки кликабелен (формат `/company/personal/user/<uid>/tasks/task/view/<id>/` подтверждён живым порталом); (д) для comment-API вопрос системных сообщений не актуален (в getlist — только человеческие комментарии). Курсор комментариев — `cursors.last_comment_id` (миграция 0002). У той же карточки позже нашлась подзадача 73689 — `tasks.task.list` с `filter: {"PARENT_ID": 42103}` (scope `task`) её отдаёт, отсюда авто-подхват подзадач (§7). Живые фикстуры сняты в `tests/fixtures/live/` (локально, в git не коммитятся — ПДн; редакция вычищает `DOWNLOAD_URL`/`VIEW_URL`/`urlDownload`/`urlShow`).

Лимиты REST (облако): leaky bucket **2 запроса/сек**, порог блокировки 50; при превышении — HTTP `503 QUERY_LIMIT_EXCEEDED`; пагинация `*.list` — 50 записей на страницу (`start`); `batch` — до 50 команд за вызов, считается одним обращением.

## 14. Telegram — API

- Отправка в конкретный топик: параметр `message_thread_id` в `sendMessage`. Без него сообщение уходит в General. Правила захвата thread_id из входящих — §5.
- **Privacy mode остаётся включённым** (дефолт BotFather): бот получает только команды, reply на свои сообщения и сервисные события — переписка партнёров до бота физически не доходит. Этого достаточно для всех фаз: команды (Фазы 0–2), `/report` и ответы на reply (Фаза 3). @упоминания бота осознанно не поддерживаются (потребовали бы отключить privacy mode и пере-добавить бота во все чаты).
- Бот должен быть добавлен в супергруппу; для отправки в известный топик достаточно членства, админка не нужна.
- **Лимит длины: 4096 символов** на сообщение («after entities parsing»). Дайджест чата отправляется **одним сообщением** (все блоки пиццерий чата склеены пустой строкой, §7 п.7); при превышении суммарной длиной рабочего лимита (`render.chunk_blocks`, 4000 символов — запас под entities) — сплит на минимальное число сообщений **по границам блоков**, а не по границам строк: блок карточки не рвётся пополам. Внутри одного блока страховка на случай, если он сам по себе длиннее лимита, — срез по границе строки, не разрывая HTML-теги (`render.clip`). 24 страны × обычно 1 сообщение (редко 2–3 при насыщенном дне) укладываются в лимиты (~20 сообщений/мин на группу) с большим запасом.
- **Форматирование: `parse_mode=HTML`.** Текст LLM экранируется `html.escape`, ссылки — `<a href="...">`. MarkdownV2 не использовать: он требует экранирования 18 спецсимволов, и LLM-текст с точками/скобками/дефисами гарантированно даёт `400 can't parse entities`.
- Лимиты: ~20 сообщений/мин на одну группу, 30/сек суммарно. При превышении — `429` с `retry_after`, экспоненциальный backoff.
- `migrate_to_chat_id`: при апгрейде группы до супергруппы `chat_id` меняется молча — ловить и обновлять в БД.

## 15. Фазы реализации

- **Фаза 0 — каркас:** входящий вебхук Битрикса (права: задачи + диск + **im**), **смоук-тест API на живой карточке** (§13) + снятие JSON-фикстур, токен бота у BotFather (privacy mode не трогать — остаётся включённым), docker-compose на MUSPELHEIM, схема БД.
- **Фаза 1 — ядро дайджеста:** планировщик с per-chat временем, дельта (история + чат задачи, клиентская резка по курсору), LLM с файлом-промптом + ретраи + fallback, отправка одним сообщением на чат со сплитом по границам блоков при переполнении (HTML, §7 п.7), сдвиг курсоров после отправки (granularity — чанк, §7 п.8), молчание в пустой день + недельный пинг, `ADMIN_CHAT_ID`-отчёты, `DRY_RUN`. Сидинг данных для проверки — базовым `/add` (собирается вместе с ядром, §16 п.4). **Это работающее ядро; полный MVP = Фазы 0–2 (§16).**
- **Фаза 2 — самообслуживание:** доводка команд `/add /remove /list /lang /time` до партнёрского качества — валидация, локализованные ответы, авто-создание чата при первой команде; флаг `restricted` + вайтлист (управление — руками в БД, §6).
- **Фаза 3 — отчёт по требованию:** `/report` (дайджест в моменте) + ответы на reply к сообщениям бота.
- **Фаза 4 — доводка:** таблица `prompts` и редактирование промпта без доступа к серверу, новые языки, опционально чтение PDF, переезд на серверы компании (сначала стоп старого polling-инстанса, потом старт нового).

## 16. Порядок сборки MVP — Фазы 0–2 (для Claude Code)

1. `docker-compose` с сервисом бота + Postgres 15+ (метка `backup.pgdump=true` для автобэкапа MUSPELHEIM); `.env` под токены.
2. Схема БД по разделу 12 + миграции.
3. Клиент Битрикса: `tasks.task.get` (+`chat.id`), `history.list` (клиентская резка дельты), `im.dialog.messages.get`, `checklistitem.getlist`, `disk.attachedObject.get`, `disk.file.get`; троттлинг 2 rps, retry на 503, `batch`. Смоук-скрипт по живой карточке + снятие фикстур (§13).
4. Telegram-бот на aiogram: long polling, команды `/add /remove /list /lang /time`, захват chat_id + thread_id по правилам §5, upsert чата, локализованные ответы из locale-файлов (§10), проверка `restricted`/вайтлиста (§6).
5. Джоба дайджеста: тик 5 мин → per-chat время → дельта → LLM (файл-промпт, `html.escape`, `max_tokens`) → одно сообщение на чат (сплит по блокам при переполнении, `render.chunk_blocks`) → сдвиг курсора после отправки (по чанку); fallback OpenAI, отчёты в `ADMIN_CHAT_ID`, недельный пинг.
6. Тесты: юнит-тесты парсера истории/дельты на JSON-фикстурах с живой карточки; `DRY_RUN`-прогон полного пайплайна; тестовый чат-«страна» с тестовым топиком — всё обкатывается там до подключения первого партнёрского чата.
