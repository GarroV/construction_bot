# Construction Bot

## 1. Что это

Construction Bot — телеграм-бот, который раз в день собирает изменения по стройкам пиццерий из
задач Битрикс24 (комментарии, статусы, чек-листы, файлы) и присылает короткую выжимку в топик
странового чата партнёра. Вместо того чтобы владелец сети или партнёр вручную открывали карточку
задачи в Битриксе, они читают одно сообщение в Telegram: что обсуждали за день, какие решения или
блокеры появились, какие файлы приложили.

Бот работает по подписке «топик ↔ карточка»: один топик может отслеживать несколько карточек
(строек), одна карточка может быть подписана в нескольких топиках. Если за сутки вообще ни по
одной карточке чата не было ничего нового — дайджест не приходит совсем (чат не заваливается
пустыми сообщениями). Если изменения есть хотя бы по одной карточке — приходит одно сообщение
на чат: карточки с изменениями получают полный блок с выжимкой, а карточки без изменений за
день — короткую строку «изменений нет» внутри того же сообщения (отдельного дайджеста ради них
не будет). Если молчание тянется дольше недели — раз в неделю приходит короткое напоминание, что
подписка жива. Всё управление — через команды прямо в чате, без отдельной админки.

## 2. Поверхности

### Команды бота

| Команда | Что делает |
|---|---|
| `/add <task_id ИЛИ ссылка>` | Подписывает текущий топик на карточку Битрикса. Карточек миллион — поиск по названию не поддерживается: принимает голый ID (`/add 8017`) либо ссылку на карточку, скопированную из браузера (ID вытаскивается регэкспом из `.../tasks/task/view/<id>/`). Если карточка не найдена или нет доступа — сообщает об этом. Повторный `/add` на уже отслеживаемую карточку — no-op с уведомлением; на ранее снятую — реактивирует подписку. Без аргументов — открывает диалог (reply-промпт), а не подсказку «Использование». Подзадачи такой карточки в Битриксе бот подхватывает **сам**, на каждом прогоне дайджеста — отдельный `/add` на них не нужен. Если чат ещё не настраивался вручную, первый успешный `/add` заодно **автонастраивает язык и таймзону чата из самой карточки** через LLM — подробности ниже. |
| `/remove <task_id>` | Снимает подписку топика с карточки. Если это ручная карточка — заодно снимает и её авто-подхваченные подзадачи. Если карточка не отслеживалась — сообщает об этом. Без аргументов — открывает клавиатуру со списком карточек (тот же флоу, что кнопка «🗑 Убрать» в `/menu`). |
| `/list` | Показывает список карточек, отслеживаемых в текущем топике. Авто-подхваченные подзадачи помечены «↳» перед названием (вместо обычного «•») — видно, что бот завёл карточку сам. |
| `/lang <код>` | Меняет язык дайджеста для чата (`ru`, `en`, ...). Влияет и на язык, на котором LLM пишет выжимку. Без аргументов — открывает клавиатуру выбора языка. |
| `/menu` | Панель с кнопками: добавить/убрать карточку, отчёт сейчас, время, язык — вся работа тыканьем, без адресных команд. Ввод номера карточки — reply на сообщение бота. Кнопка «📊 Отчёт сейчас» не гонит отчёт сама — сначала показывает выбор охвата (тот же экран, что и голый `/report`). |
| `/report [<task_id ИЛИ ссылка>]` | Дайджест прямо сейчас, не дожидаясь дневного расписания. Без аргумента (как и кнопка «📊 Отчёт сейчас») открывает выбор: «По всем» — отчёт по всему топику как раньше; кнопка конкретной карточки — точечный отчёт только по ней (дискавери подзадач при этом пропускается, отчёт получается быстрее). В списке кнопок — только РУЧНЫЕ карточки: авто-подхваченные подзадачи отдельным пунктом не показываются, они подразумеваются родителем и едут вместе с ним, когда выбран он. С аргументом (ID или ссылка, как у `/add`) отчёт по этой карточке запускается сразу — по родителю заодно уходят и его авто-подхваченные подзадачи, по самой подзадаче (адресована напрямую) — только она; если карточка не отслеживается в топике — сообщает об этом. Дневной дайджест не ломает. **Явный запрос отчёта всегда возвращается с содержимым** — карточка без новых изменений получает не короткую строку, а сводку текущего состояния (последние комментарии + чек-лист, LLM-текст по `prompts/overview.txt`), а не тишину. Только если карточке буквально нечего показать (её никогда не обсуждали) — она получает информативную строку с датой последнего дайджеста («…изменений нет (ДД.ММ ЧЧ:ММ)», либо «с момента подключения», если дайджеста ещё не было); тот же текст — последний fallback чата, если охват отчёта вообще не дал ни одной карточки. |
| `/time <ЧЧ:ММ> [город, страна ИЛИ таймзона]` | Задаёт локальное время дайджеста для чата. Второй аргумент понимает и человеческие названия («Белград», «Belgrade»), и IANA-идентификатор («Europe/Belgrade») — резолвится через `resolve_tz` (`src/telegram/tz_aliases.py`, города/страны сети Dodo International). Нужно указать явно при первой настройке (пока чат на дефолтной UTC, если она не была подхвачена автоматически — см. ниже); дальше можно менять только время, сохраняя ранее заданную таймзону. Без аргументов — открывает reply-промпт (тот же флоу, что кнопка «🕘 Время» в `/menu`). |

Все ответы бота локализованы (`locales/ru.json`, `locales/en.json`) и идут `reply` на исходное
сообщение с командой. Голая команда без аргументов (`/add`, `/time`, `/lang`, `/remove`) всегда
открывает диалог, а не показывает usage-подсказку — та подсказка остаётся только для непустых
невалидных аргументов (например `/time 9:99` или `/add фигня`).

**Автоопределение таймзоны при первом контакте.** Telegram не отдаёт таймзону пользователя, но
домен бота ограничен странами сети Dodo International — значит название чата почти всегда и есть
страна/город. При первом создании записи чата (`repo.upsert_chat` возвращает `created=True`) бот
пробует резолвить название супергруппы через `resolve_tz` (`src/telegram/tz_aliases.py`) и, если
получилось, тихо выставляет найденную таймзону (время остаётся дефолтным `09:00`) — без
дополнительного сообщения партнёру, таймзона видна позже через `/time`. Не резолвится (например
служебный чат вроде `group_za_test`) — чат остаётся на дефолтной `UTC`, как и раньше.

**Автонастройка чата из карточки при первом `/add`.** Название чата — грубое приближение (страна
целиком), а вот название карточки Битрикса обычно называет конкретный город стройки, и обсуждение
в ней уже показывает, на каком языке общается команда — этого достаточно, чтобы уточнить и язык, и
таймзону одним LLM-вызовом. Если чат ещё не был настроен вручную (`chats.auto_configured = FALSE`),
после успешного `/add` бот берёт название карточки и до 10 последних комментариев обсуждения и
одним structured-output вызовом (`llm.detect_card_locale`, `src/digest/llm.py`) определяет: **язык**
(`ru`, если обсуждение преимущественно русское, иначе `en` — только эти два значения) и **IANA-
таймзону** города из названия карточки (например «Podgorica-2» → `Europe/Podgorica`; город неясен
→ ничего). Успешный детект тихо применяет язык (`/lang`-эквивалент) и, если таймзона резолвилась и
прошла валидацию, время `09:00` в ней (`/time`-эквивалент) — без дополнительных сообщений партнёру,
ответ `/add` не меняется. После этого (независимо от исхода) `auto_configured` становится `TRUE` —
детект больше не запускается для этого чата. **Ручная настройка побеждает всегда**: `/lang` и
`/time` сами ставят `auto_configured = TRUE`, что сразу и навсегда отключает автонастройку из
карточки. **Деградация тихая**: LLM недоступен после ретраев, вернул мусор, сеть или БД подвели —
`/add` не падает и не тормозит сверх обычного, настройки чата не меняются, флаг остаётся `FALSE` —
бот попробует снова при следующем `/add`.

### Автоматические сообщения

| Событие | Когда приходит |
|---|---|
| Дайджест чата | Раз в день, в момент `digest_time` чата (по его таймзоне), если хотя бы по одной из карточек чата были изменения (статус/дедлайн/чек-лист), новые комментарии в чате задачи или новые файлы. Блоки всех карточек чата (включая «изменений нет» и авто-подхваченные подзадачи) склеиваются пустой строкой в **одно сообщение**; сплит на несколько сообщений — только при превышении лимита длины, по границам блоков (карточка не рвётся пополам). |
| Недельный пинг | Если у чата есть хотя бы одна активная карточка, но ≥ `WEEKLY_PING_DAYS` (по умолчанию 7) дней не было ни одного содержательного дайджеста и ни одного предыдущего пинга — присылается одна строка вида «по стройкам без изменений с {дата}». |
| Сводка об ошибках | В `ADMIN_CHAT_ID` — только если в прогоне тика были ошибки (сбой Битрикса/LLM/отправки по конкретным карточкам или чатам). |

## 3. Сквозной сценарий

1. Партнёр (или админ) в топике страны пишет `/add 8017`.
2. Бот запрашивает у Битрикса задачу `8017` (`tasks.task.get`), сохраняет alias (заголовок задачи),
   запоминает текущие `last_history_id`/`last_message_id` как стартовый курсор и подтверждает
   подписку: «Отслеживаю: <название> (#8017)».
3. Планировщик тикает каждые `SCHEDULER_TICK_MINUTES` минут (по умолчанию 5) и для каждого
   активного чата проверяет, наступило ли его локальное `digest_time` и не выполнялся ли уже прогон
   сегодня.
4. Перед сбором дельты бот проверяет подзадачи ручных карточек чата (`tasks.task.list` с
   `PARENT_ID`) и сам подписывает топик на новые — они появляются в `/list` с пометкой «↳» и живут
   своей жизнью дальше (отдельные `/remove` тоже возможны).
5. Когда время подошло: бот забирает у Битрикса историю задачи и сообщения чата задачи начиная с
   сохранённого курсора, собирает «дельту» (что изменилось + что написали + какие файлы прислали —
   новая карточка даёт прямую ссылку на файл, старая — ссылку на комментарий с файлом).
6. Если дельта по карточке не пустая — дельта уходит в LLM (`prompts/digest.txt`) с просьбой сделать
   выжимку на языке чата; при недоступности LLM после ретраев — fallback на сырой список изменений
   с пометкой «краткая версия без выжимки». Так по каждой карточке чата получается свой блок текста
   (карточки без изменений получают короткую строку «изменений нет» — без вызова LLM).
7. Блоки всех карточек чата склеиваются пустой строкой в **одно сообщение** (`html.escape`,
   лимит 4096 символов на сообщение) и отправляются в топик чата; если суммарная длина превышает
   рабочий лимит — сплит на минимальное число сообщений **по границам блоков** (блок карточки не
   рвётся пополам), сообщения уходят последовательно. Только после подтверждённой успешной отправки
   сообщения курсоры **всех карточек, чей блок в него вошёл**, сдвигаются разом — сбой одного
   сообщения (при сплите) не блокирует и не теряет дельту карточек из уже отправленных сообщений.
8. Партнёр читает дайджест в своём топике, ничего не открывая в Битриксе.

## 4. Запуск

### Переменные окружения

Скопировать `.env.example` в `.env` и заполнить (см. актуальный список ключей в самом файле):

```bash
cp .env.example .env
```

Ключевые переменные:

- `BITRIX_WEBHOOK_URL` — входящий вебхук Битрикс24 (`https://<portal>/rest/<user_id>/<token>/`).
- `TELEGRAM_BOT_TOKEN` — токен бота от BotFather.
- `OPENAI_API_KEY` / `OPENAI_MODEL` — доступ к LLM для выжимок (модель по умолчанию `gpt-5.6-terra` — не reasoning-модель: весь бюджет токенов идёт в текст выжимки, а не в скрытые рассуждения; так же, как в Sorum).
- `POSTGRES_DSN` — строка подключения к Postgres (в `docker-compose.yml` — `postgres` как хост).
- `SCHEDULER_TICK_MINUTES` — период тика планировщика (по умолчанию 5).
- `DEFAULT_LANGUAGE` — язык нового чата до первого `/lang` (по умолчанию `ru`).
- `ADMIN_CHAT_ID` — telegram id, куда приходят сводки об ошибках прогона (необязательно).
- `WEEKLY_PING_DAYS` — порог тишины для недельного пинга (по умолчанию 7).
- `DRY_RUN` — `true`/`false`. В режиме `DRY_RUN=true` полный пайплайн (Битрикс + LLM) отрабатывает
  как обычно, но вместо отправки в Telegram текст дайджеста печатается в stdout контейнера — удобно
  для обкатки без риска заспамить реальные чаты.

### Локальный запуск

```bash
docker compose up -d --build
docker compose logs -f bot
```

`docker-compose.yml` поднимает два сервиса: `bot` (само приложение, точка входа — `python -m
src.main`) и `postgres` (с healthcheck и лейблом `backup.pgdump=true` для автобэкапа на
MUSPELHEIM). При старте `src/main.py` сам накатывает недостающие миграции из `migrations/` перед
тем как поднять polling и планировщик — отдельного шага миграции руками не требуется.

### Смоук-скрипт Битрикса

`scripts/smoke_bitrix.py` — разовая проверка вебхука по живой карточке (историю задачи, сообщения
чата задачи, файлы, чек-лист) с сохранением обезличенных фикстур в `tests/fixtures/live/`:

```bash
.venv/bin/python -m scripts.smoke_bitrix <task_id>
```

### Тесты

Юнит-тесты, не требующие БД:

```bash
.venv/bin/pytest -v
```

Тесты, помеченные `db` (например `tests/test_db.py`, `tests/test_repo.py`), требуют переменную
`TEST_POSTGRES_DSN`, указывающую на тестовую Postgres (не на продовую БД из `docker-compose.yml`):

```bash
TEST_POSTGRES_DSN=postgresql://bot:bot@<host>:5544/botdb .venv/bin/pytest -v
```

## 5. Эксплуатация

- **Сводки об ошибках.** Если `ADMIN_CHAT_ID` задан, после каждого тика планировщика с ошибками
  (недоступный Битрикс/LLM по конкретной карточке, чат кикнул бота и т.п.) в этот чат/личку
  приходит сообщение со списком проблем за прогон. Пустой прогон без ошибок сводку не шлёт.
- **Ограничение доступа к командам (`restricted`).** Флаг `chats.restricted` по умолчанию `FALSE`
  (команды доступны всем в чате). Если по конкретной стране понадобится ограничить управление
  списком отслеживаемых карточек, флаг переключается и заполняется `chat_admins` — **руками в БД**,
  кода это не касается (сознательное решение MVP — команда управления вайтлистом появится только
  если ограничение реально понадобится):

  ```sql
  UPDATE chats SET restricted = TRUE WHERE id = <chat_id>;
  INSERT INTO chat_admins (chat_id, telegram_user_id) VALUES (<chat_id>, <telegram_user_id>);
  ```

- **Один polling-инстанс.** aiogram long polling не терпит двух одновременно запущенных процессов
  на одном токене — перед стартом на новом окружении (например при переезде с локального
  DRY_RUN-контейнера на MUSPELHEIM) предыдущий инстанс нужно останавливать (`docker compose down`).
- **Ручной сброс дайджеста для теста** — если нужно прогнать дайджест повторно в тот же
  календарный день, не дожидаясь следующих суток: `UPDATE chats SET last_digest_date = NULL WHERE
  id = <chat_id>;`.
- **Ручной сброс автонастройки чата (`chats.auto_configured`, миграция 0005).** Если нужно снова
  прогнать LLM-детект языка/таймзоны из карточки на следующем `/add` (например для теста, или чат
  раньше получил детект с ошибочным результатом) — руками в БД: `UPDATE chats SET auto_configured =
  FALSE WHERE id = <chat_id>;`. Обратная операция (`= TRUE`) навсегда отключает автонастройку для
  чата, не трогая ручной `/lang`/`/time` — тот же эффект, что и от самих этих команд.
- **Битая `chats.timezone` не глушит бота.** `chats.timezone` пишется только через `/time`
  (валидируется `resolve_tz`), но ручная правка в БД — легальный сценарий (как у `restricted`
  выше) и теоретически может занести невалидное значение. `src/digest/scheduler.safe_zoneinfo`
  оборачивает каждое обращение к `chats.timezone` (тик, `/report`/кнопки, `force_report.py`):
  невалидная таймзона не роняет прогон исключением `ZoneInfoNotFoundError`, а деградирует на UTC
  с `WARNING` в лог (сигнал не теряется молча).
- **Кэш LLM-выжимок (`llm_cache`, миграция 0004, TTL 24h).** Повторные «Отчёт сейчас» по
  неизменившимся данным не дёргают OpenAI повторно — выжимка берётся из кэша по хэшу финального
  промпта (`src/digest/llm.material_hash`, `scheduler._summarize_cached`). Тот же кэш спасает
  и от простоя провайдера: если по идентичному промпту уже был успешный вызов, повторный сбой
  OpenAI (например 500) отдаёт готовый текст вместо fallback-версии «без выжимки». Bitrix
  при этом дёргается на каждом прогоне как обычно — он и остаётся источником инвалидации:
  изменилось хоть что-то в сырье (комментарий, статус, чек-лист) — хэш другой, кэш промахивается.
  Сбой самого кэша (БД недоступна) не ломает генерацию — бот просто работает без кэша с
  `WARNING` в лог. Ручной сброс не нужен: `TRUNCATE llm_cache;` при необходимости всё же
  почистить кэш руками.

### Результаты смоук-теста

Прогнан 2026-07-23 (`scripts/smoke_bitrix.py 42103`, портал `b24.dodoteam.ru` — коробочный):

- Карточки **старого типа**: у задач нет чата → комментарии читаются через `task.commentitem.getlist`
  (курсор `cursors.last_comment_id`, миграция 0002); BB-коды снимаются перед LLM.
- `COMMENT` в `tasks.task.history.list` есть; чек-лист и история читаются штатно.
- `disk.file.get` на файлы из комментариев — ACCESS_DENIED → вместо прямой ссылки на файл
  дайджест даёт ссылку на **комментарий-источник** внутри карточки (`?commentId=<id>#com<id>`,
  `links.comment_url`) — так владелец решил закрыть проблему недоступного `disk.file.get`.
- `tasks.task.list` с `filter: {"PARENT_ID": <id>}` (scope `task`) отдаёт подзадачи родителя —
  проверено живьём: у 42103 подзадача 73689. На этом строится авто-подхват подзадач (§2, `/list`).
- Портал за антиботом Servicepipe: клиент Битрикса ходит **GET-ом с браузерным User-Agent**
  (POST режется JS-challenge'ем). Запрошено WAF-исключение по маркеру `construction-bot` в UA.
- Права вебхука: **«Задачи (task)»** — не путать с соседним «Задачи (tasks)», тот даёт
  `insufficient_scope`. Плюс Диск (disk) и Чат и уведомления (im).
- Живые фикстуры — `tests/fixtures/live/` (только локально, в git не идут — ПДн; редакция
  вычищает URL с токеном вебхука: `DOWNLOAD_URL`/`VIEW_URL`).
